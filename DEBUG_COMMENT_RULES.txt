Laserdrilling 디버깅 주석 규칙
작성 기준일: 2026-11-19

1. 목적

디버깅할 때 흐름, 통신, 좌표 변환, 상태 전이, 파일 저장 지점을 빠르게 찾기 위한 규칙이다.
주석은 코드가 무엇을 하는지 반복하지 않고, 왜 그 순서가 필요한지와 반드시 지켜야 할 조건을 기록한다.

2. 기본 형식

// @<태그> [<기능명>] <단계> - <이유, 보장 조건 또는 실패 위험>

예시

// @흐름 [리뷰검사] 준비 - 검사 시작 시 Recipe와 Setting 값을 동결한다.
// @통신 [비전검사] 요청 - 선택한 Beam 번호로 검사 요청을 전송한다.
// @좌표 [리뷰검사] 설계→스테이지 - Design Y+를 Stage 축 방향으로 변환한다. 단위: mm
// @보호 [옵셋적용] 중복검사 - 동일 Source Result의 적용 이력을 확인한다.

3. 표준 태그

@흐름   : Sequence의 시작, 주요 단계, 완료 순서
@통신   : 장치 요청, 응답, Handshake, Timeout, 연결 해제
@상태   : 상태 전이, 소유권, 실행 중 변경 금지 조건
@좌표   : 좌표계, 축 방향, Flip, 단위, Offset 적용 순서
@보호   : 중복 실행, 잘못된 값, 오래된 데이터, 위험 동작 차단
@파일   : 파일 선택, Revision, 원자 저장, Rollback, 이력
@알람   : 알람 발생 조건, 등급, AUTO 정지 여부
@스레드 : Lock, Dispatcher, 비동기 실행, 취소 소유권
@성능   : Cache, 지연 로딩, 대량 데이터 처리 이유
@시뮬   : Simulation과 실제 통신의 분기 및 공통 완료 조건

4. 표준 기능명

[자동공정] [수동MOF] [리뷰검사] [재검사] [결과편집]
[옵셋적용] [리뷰옵셋] [얼라인왜곡] [디폴트옵셋]
[보호윈도우] [비전검사] [스테이지이동] [알람] [결과파일]
[MELSEC] [Automation] [스크립트] [레시피] [Setting]

새 기능명은 기존 기능명으로 표현할 수 없을 때만 추가한다.
같은 기능을 Review, 리뷰, REVIEW처럼 여러 이름으로 만들지 않는다.

5. 표준 단계명

준비, 조건동결, 요청, 응답대기, 검증, 계산, 저장, 완료, 롤백, 정리

단계명은 짧게 쓰고 자세한 내용은 하이픈 뒤에 적는다.

6. 작성 위치

- 복잡한 메서드의 첫 핵심 동작 바로 위
- 외부 장치에 명령을 보내기 직전
- 좌표계나 단위가 바뀌는 계산 바로 위
- 파일을 활성값으로 바꾸거나 Rollback하는 동작 바로 위
- NG, 알람, 중복 적용처럼 공정을 막는 조건 바로 위
- Lock, CancellationToken, Dispatcher 소유권이 중요한 위치

7. 작성 원칙

- 한글 위주로 작성하되 Recipe, Setting, Vision, MELSEC, Beam, Shot, Head 같은 코드 용어는 원문을 유지한다.
- 값의 단위가 중요하면 mm, um, pixel, ms를 적는다.
- 순서가 중요하면 A -> B -> C 형태로 명시한다.
- 코드 변경 시 보장 조건이 달라지면 주석도 같은 변경에서 수정한다.
- 한 주석은 가능하면 한 줄, 최대 두 줄로 제한한다.

8. 피해야 할 주석

잘못된 예

// 값을 저장한다.
// 반복문을 실행한다.
// 에러가 나면 예외를 던진다.
// 임시 처리

코드만 읽어도 알 수 있는 동작 설명, 담당자 이름, 날짜만 있는 메모, 근거 없는 TODO는 남기지 않는다.

9. 검색 예시

rg "@흐름"
rg "@통신 \[비전검사\]"
rg "@좌표"
rg "\[옵셋적용\]"
rg "@보호.*중복"

10. 검토 체크

- 태그와 기능명이 이 문서의 표준 용어인가?
- 코드가 아니라 이유와 보장 조건을 설명하는가?
- 실제 Simulation/실통신 동작과 일치하는가?
- 좌표 방향과 단위가 명확한가?
- 오래된 정책을 설명하는 주석이 남아 있지 않은가?

11. 증상별 디버깅 진입점

아래 순서는 증상 발생 시 처음 열 파일과 다음 확인 위치를 정한 것이다.
라인 번호는 변경될 수 있으므로 메서드명 또는 표준 주석 태그로 검색한다.

11.1 AUTO DoReady, Process 또는 Review가 멈춤

첫 진입점
- Drilling.Common/Station/CStationProcess.cs
- RunProcess, RunReview, DoReady, WaitSignal 검색

확인 순서
1) 현재 Action과 마지막 완료 Action을 확인한다.
2) 대기 중인 MELSEC ID의 Value, State, SampleAt, AgeMs를 확인한다.
3) Stage 이동이면 CStageReviewSequences.cs의 @통신 [스테이지이동]으로 이동한다.
4) 가공 Task이면 CAutomationManager.cs의 @흐름 [Automation]으로 이동한다.

검색
rg -n "@통신 \[자동공정\]|RunProcess|RunReview|WaitSignal" Drilling.Common/Station
rg -n "@통신 \[스테이지이동\]" Drilling.Common/Station/CStageReviewSequences.cs

11.2 Stage 또는 Review 이동 Timeout, 오위치, STOP 미복귀

첫 진입점
- Drilling.Common/Station/CStageReviewSequences.cs
- Move, WaitArrival, Abort 검색

확인 순서
1) MoveAble, MoveStart, MoveComplete, MoveAck 순서를 확인한다.
2) 참여 축 Busy가 0인지 확인한다.
3) Current X/Y가 Target X/Y의 +/- 0.0005 mm 이내인지 확인한다.
4) 실패 후 STOP, START, ACK가 모두 복귀했는지 확인한다.

검색
rg -n "@통신 \[스테이지이동\]|@보호 \[스테이지이동\]" Drilling.Common/Station/CStageReviewSequences.cs

11.3 IOF 또는 Flying 검사 실패, 촬영 개수 불일치

첫 진입점
- Drilling.Common/Station/CStageReviewSequences.cs의 PrepareIof
- Drilling.Common/Review/CReviewManager.cs의 MeasureVisionLine, ParseVisionLineResponse

확인 순서
1) IOF 좌표 개수와 IOF_TRIGGER_POINT_COUNT를 비교한다.
2) IOF_POS_ARRAY_1 Write 값과 Readback 값을 비교한다.
3) IofStart, IofComplete, IofAck 해제 순서를 확인한다.
4) Vision 응답의 nFindHoleCount와 요청 Shot 수를 비교한다.

검색
rg -n "PrepareIof|MeasureVisionLine|ParseVisionLineResponse|@통신 \[스테이지이동\]" Drilling.Common

11.4 Vision RESULT NG, Mark 없음, 결과가 모두 0

첫 진입점
- Drilling.Common/Interface/Vision/CVisionComm.cs
- Drilling.Common/Review/CReviewManager.cs

확인 순서
1) 요청 Beam, Method, Target 좌표를 확인한다.
2) 응답 ResultCode, Hole 개수, Vision Mark 유무를 확인한다.
3) Camera Resolution, Vision Flip, X/Y 변환 순서를 확인한다.
4) 통신 NG와 측정값 NG가 같은 상태로 처리되지 않았는지 확인한다.

검색
rg -n "@통신 \[비전검사\]|@좌표 \[비전검사\]|ResultCode|CreateVisionMeasurement|ApplyMeasurementError" Drilling.Common

11.5 Automation Script Upload, RUN 또는 Task 정지 실패

첫 진입점
- Drilling.File/Script/CAutomation1ScriptFile.cs의 Build, LoadLatest
- Drilling.Common/Automation/CAutomationManager.cs의 UploadScript, RunStagePreparedScript, StopStagePreparedTask

확인 순서
1) 선택한 Build 폴더와 Manifest가 같은 회차인지 확인한다.
2) Head, Controller, Task, Script 파일명, MOF RunId가 현재 Recipe와 일치하는지 확인한다.
3) Controller Task가 Idle에서 시작했는지 확인한다.
4) STOP 후 새 Status가 Idle, ProgramComplete, QueueComplete 또는 Stopped인지 확인한다.

검색
rg -n "@흐름 \[Automation\]|@보호 \[Automation\]" Drilling.Common/Automation
rg -n "@파일 \[스크립트\]|@보호 \[스크립트\]" Drilling.File/Script

11.6 Offset 미적용, 중복 적용, Rollback 후 이전 Offset 사용

첫 진입점
- Drilling.File/ReviewOffset/CReviewOffsetFile.cs
- Drilling.UI/Menu/Menus/CMenuCorrection.ReviewData.Offset.cs
- Drilling.Common/Station/CStationProcess.cs의 Offset 준비 상태

확인 순서
1) Source Result 파일과 일별 _apply 이력을 확인한다.
2) 활성 Offset 파일명과 SavedAt을 확인한다.
3) Rollback 후 Recipe Cache와 DoReady 준비 상태가 무효화됐는지 확인한다.
4) AUTO 중복이면 Heavy Alarm과 NG가 함께 발생했는지 확인한다.

검색
rg -n "@보호 \[옵셋적용\]|@파일 \[리뷰옵셋\]|_apply|Rollback" Drilling.Common Drilling.File Drilling.UI

11.7 재검사 또는 결과 편집 후 화면과 파일 보정값 불일치

첫 진입점
- Drilling.File/ReviewResult/CReviewResultFile.cs의 SaveRevision
- Drilling.UI/Menu/Menus/CMenuCorrection.ReviewData.Offset.cs의 MeasuredRows

확인 순서
1) 결과 Source가 MEASURED, RETAINED, EDITED 중 하나인지 확인한다.
2) UNMEASURED와 ERROR가 보정에서 제외되는지 확인한다.
3) 화면 Preview와 저장 파일이 같은 후보 Shot 집합을 사용했는지 확인한다.
4) mm 저장 정밀도와 um 표시 반올림을 구분한다.

검색
rg -n "MEASURED|RETAINED|EDITED|MeasuredRows|SaveRevision" Drilling.File Drilling.UI

11.8 Shot, Beam, Review 또는 Stage 좌표가 예상과 다름

첫 진입점
- Drilling.Common/Recipe/CShotCoordinatePlanBuilder.cs
- Drilling.Common/Correction/CAlignInterpolation.cs
- Drilling.Common/Review/CReviewManager.cs

확인 순서
1) Design -> Scanner -> Stage 또는 Review 변환 순서를 확인한다.
2) 담당 Head와 선택 Beam의 First Beam Offset을 확인한다.
3) Vision Flip과 축 부호를 확인한다.
4) Recipe, Head Default, Align, Review, Shift Offset의 적용 대상과 순서를 확인한다.

검색
rg -n "@좌표|FirstBeam|VisionFlip|ShiftOffset" Drilling.Common

11.9 Recipe 또는 Setting 저장, 복사, 재시작 후 값 불일치

첫 진입점
- Drilling.Common/Managers/CRecipeManager.cs
- Drilling.Common/Managers/CSettingManager.cs
- Drilling.File/JHMI/CJhmiRecipeFile.cs
- Drilling.File/JHMI/CSettingFile.cs

확인 순서
1) 저장 전 Validation을 통과했는지 확인한다.
2) 파일 Write 후 Readback이 성공했는지 확인한다.
3) Readback 이후 Cache가 게시됐는지 확인한다.
4) Recipe 복사 시 Review Offset의 _apply 이력이 제외됐는지 확인한다.

검색
rg -n "@보호 \[레시피\]|@파일 \[레시피\]|@보호 \[Setting\]|@파일 \[Setting\]" Drilling.Common Drilling.File

11.10 Protect Window 재시도 또는 매수 이상

첫 진입점
- Drilling.Common/Station/CStationProcess.cs
- Drilling.File/JHMI/CJhmiRecipeFile.cs의 ChangeProtectWindowCount

확인 순서
1) 교체 완료 응답의 Tray Count를 확인한다.
2) Max Process Count와 Retry Count를 확인한다.
3) 재시도 소진 후 Warning Alarm만 발생하고 AUTO는 계속되는지 확인한다.
4) Count 행만 원자 저장되고 다른 Recipe 값은 유지되는지 확인한다.

검색
rg -n "@보호 \[보호윈도우\]|@파일 \[보호윈도우\]|ProtectWindow" Drilling.Common Drilling.File

11.11 Alarm은 떴지만 History 또는 분석 화면에 없음

첫 진입점
- Drilling.Common/Alarm/CAlarmManager.cs
- Alarm History UI와 Log Analysis 데이터 로더

확인 순서
1) Alarm Code가 ALARM_LIST에 있는지 확인한다.
2) 발생 시각, 해제 시각, Severity가 저장됐는지 확인한다.
3) UI 시간 범위와 로그 파일 날짜가 일치하는지 확인한다.

검색
rg -n "@알람 \[알람\]|ALARM_LIST|AlarmHistory" Drilling.Common Drilling.UI Drilling.File

11.12 Review 화면 전환 또는 대량 결과 Load가 느림

첫 진입점
- Drilling.UI/Menu/Menus/CMenuReview.cs
- Drilling.File/ReviewResult/CReviewResultFile.cs

확인 순서
1) UI Thread에서 파일 전체 Parse 또는 Shot 전체 재생성을 하는지 확인한다.
2) 취소된 이전 Load가 계속 실행 중인지 확인한다.
3) Progress가 실제 Load Task 생명주기와 같이 닫히는지 확인한다.
4) 지연 렌더링과 Cache가 결과 선택 변경 시 무효화되는지 확인한다.

검색
rg -n "@성능|Progress|LoadResult|CancellationToken" Drilling.UI/Menu/Menus/CMenuReview.cs Drilling.File/ReviewResult
